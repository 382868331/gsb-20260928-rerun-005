# 机器人任务编排平台（首轮：虚拟机器人）

把几个动作（移动 / 取物 / 放置 / 等待条件 / 播报）接成流程，实时查看每个节点的执行、等待、失败与失败后走向；支持暂停/恢复（接回原状态）和优雅取消（当前动作收尾后停止，不继续后续动作）。状态全部持久化在服务端 SQLite，刷新页面、重启后端都不丢。

## 架构

- `backend/main.py` — FastAPI：流程/执行 REST API + `/ws/events` 实时事件推送
- `backend/engine.py` — 异步编排引擎：节点状态机、success/failure 分支、等待条件、暂停恢复、优雅取消
- `backend/simulator.py` — 虚拟机器人：坐标/持物/空闲状态，动作分步推进，可注入障碍物、可收尾取消
- `backend/store.py` — SQLite 持久化：flows / executions / node_runs / events / recovery_states；重启后遗留运行态停在 `awaiting_recovery` 等待人工核实
- `frontend/` — React 19 + @xyflow/react 流程画布，节点颜色表示 运行/等待/失败/取消，失败边红色虚线并高亮实际走向
- `tests/test_engine.py` — 等待+失败分支、取物遇障碍后取消、暂停恢复三个场景

## 运行

```bash
# 后端
.venv/bin/python -m uvicorn backend.main:app --port 8000

# 前端（另开终端，已配置 /api、/ws 代理到 8000）
cd frontend && npx vite
```

打开 http://localhost:5173 ，内置「取物任务」演示流程：
移动到货架 → 等待绿灯 → 取物 → 送达放置；取物失败走红色虚线分支（绕行播报 → 回到「移动到货架」重新执行），`max_retries=2`（共 3 次尝试）用尽后走「超过上限」边停在「等待人工排障」节点，由人工选择放行继续或确认终止。

同一节点在回路中被多次执行时，画布上以**第 N 次**标记区分：节点主体只显示本轮（执行引擎当前轮次）状态，历次经过以小徽章列在节点内；边的高亮以实际发生的 `branch_taken`/`retries_exhausted` 事件为准，旧回路走向不会被新一轮结果覆盖。暂停/恢复与优雅取消均按 `(节点, 轮次)` 精确落库，迟到的动作回调无法写入新一轮。

### 取消与迟到结果

取消决定一旦作出即为最终状态：执行记录定格在 `cancelled`，**即使尚未返回的移动等动作稍后报告成功**，也不会把该节点改成成功、不会继续走 success 分支、不会重复产生完成事件。迟到结果通过 `late_result_recorded` 事件和 `node_followups` 表保存为**可追溯的后续信息**（`kind=late_result`，含成功/失败与详情），节点终态与执行终止原因保持取消那一刻的决定。`node_runs` 的终态（succeeded/failed/cancelled/aborted）在存储层受保护，任何迟到写入都会被拒绝并转入后续信息表。

### 失败后的收尾流程

动作失败后、进入失败分支/重试前，先执行收尾：**就地放下持有物 → 返回安全位置（默认 (0,0)）**。收尾进度通过 `cleanup_started/cleanup_progress/cleanup_succeeded/cleanup_failed/cleanup_cancelled/cleanup_skipped` 事件呈现，并作为该失败节点的后续信息（`kind=cleanup`）落库。收尾**不改变**失败判定：收尾成功不会把节点改成成功，收尾失败或被取消也**不会覆盖原失败原因**，失败分支/重试次数照常推进。

取消在不同阶段到达时允许执行的动作：

- **重试回路中取消**：不再启动后续节点；若失败已发生，收尾不再启动（`cleanup_skipped`），终止说明保留原失败原因。
- **等待条件期间取消**：等待立即结束，不触发任何机器人收尾动作（当时并未执行动作）。
- **收尾过程中取消**：允许当前正在执行的那一个收尾动作做完（优雅收尾），后续收尾动作不再启动；再次到达的取消会立即终止后续动作。
- 暂停对收尾同样生效，恢复后接着完成剩余收尾步骤。

### 重启前人工核实与恢复一致性

每次终止都在 `executions.termination_reason` 写入确定的终止说明（含取消阶段与被保留的原失败原因），并随 `execution_finished` 事件发出。进程重启不会把等待、动作中、重试或收尾中的执行直接记为中断：这些执行先进入 `awaiting_recovery`，界面展示持有物、最后已确认位置、当前 `(节点, 轮次)`、尚未确认的动作以及原故障；核实期间收到的迟到回应只通过 `late-action` 写入该旧执行的 `node_followups`，不会替操作者发起新的移动。

操作者必须明确选择：

- **继续收尾/继续**：保存恢复决定，恢复设备快照；已确认完成的 `release`/`return` 阶段会从检查点跳过，不重复放下物体或移动，然后按原本的成功/失败/重试分支顺序继续。
- **结束本次流程**：保留原节点失败、未确认动作和原故障原因，执行安全收尾后记录为 `resolved`。
- **再次取消/已存在取消决定**：继续完成必要收尾后仍记录为 `cancelled`，取消阶段和原故障分别保留。

恢复决定、人工排障决定和收尾阶段都持久化在 `recovery_states`。连续重启不会重复要求已经处理的决定，也不会重复调用已确认的放下动作；迟到结果永远只补充到对应的旧 `(节点, 轮次)` 记录。

### 核实证据的逐项登记与修订

重启待核实时，**位置、持物、动作结果**分别登记在 `recovery_evidence` 台账：每条证据记录主题、来源（`manual_observation` 现场观察 / `device_response` 设备迟到回应 / `checkpoint` 检查点快照）、观察时刻、内容与状态（有效/已撤回/已被修订）。重启水合时自动从最后检查点播种位置与持物证据；设备迟到的动作完成回应只登记为 `action_result` 证据并写入旧 `(节点,轮次)` 的 `node_followups`，**不会**替操作者发起新移动，也不会凭“最后到达”自动覆盖现场观察。

- **矛盾保持待决定**：同一主题下仍有效的证据内容冲突时归并为 `disputed`（例如现场观察确认空手、稍后旧动作回报取物完成），缺少证据为 `unknown`。证据矛盾或不足时，继续/结束决定被拒绝（`recovery_decision_blocked`），状态停在 `awaiting_recovery`。
- **撤回与修订**：现场观察可以撤回（保留台账历史，标记 `withdrawn`）；修订通过新增证据实现，旧条目标记 `superseded`。撤回后矛盾消失即可重新作决定。
- **展示决定依赖**：保存恢复决定时发出 `recovery_decision_saved`，其 `basis` 与 `evidence` 明确列出该决定依赖了哪些主题的哪几条证据（证据序号、来源、观察时刻）。前端待核实栏按位置/持物/动作结果三格展示「已确认 / 矛盾·待决定 / 无有效证据」及依据的证据编号。
- **证据更正后重待确认**：决定保存后、后续动作发出前若证据被修订（`evidence_revision` 变化），尚未发出的动作凭恢复决定令牌（`recovery_token`）识别失效并回到等待确认（`recovery_reawait_confirmation`）；受阻动作通过 `recovery_followups_blocked` 明确展示（如「后续移动」「就地放下(release)」「再次取物(pick)」）。每次决定只推进一次，补充证据并重新确认后才继续。
- **已完成的事实保留**：已经完成的移动节点、已经执行过的放下/返回收尾记录，不因证据更正而回退或重跑；受影响的只是尚未发出的后续动作。`node_runs` 终态保护与 `node_followups` 追溯不变。
- **持物争议**：持物归属为 `disputed` 时，不得再次取物、也不得重复放下；恢复收尾的每个阶段（放下需要持物已确认、返回需要位置已确认）在动作发出前经过决定闸门，争议未决时动作不启动。
- **核实期间再次取消**：`awaiting_recovery` 下的取消落库为 `cancel_during_recovery`，尚未发出的动作不再启动；完成必要收尾后仍记录为 `cancelled`，原故障与取消阶段分别保留。
- **重启时点**：重启发生在核实决定保存后、动作发出前或收尾中时，引擎水合恢复决定与令牌，接续原阶段而不重复询问；终止说明区分「原故障」「依据证据」「后续处置（结束/取消）」三部分。

## 验收操作路径

1. 点「运行」，流程走到「等待货架绿灯」时节点黄色脉动，顶部出现「满足条件」按钮。
2. 打开「障碍物：开」，再点满足条件：取物失败，节点变红，红色失败边高亮，经绕行播报回到移动节点；连续 3 次失败后停在「等待人工排障」，顶部出现「已排障，放行继续 / 确认终止」入口（每一轮回路都需要再点一次「满足条件」）。
3. 另开一次运行，取物途中打开障碍物并点「取消」：当前动作收尾，执行记录为 cancelled，即使之后迟到的步骤结果到达，也不会把旧回路记成新一轮完成，后续节点从未启动。
4. 运行或等待条件中点「暂停」：机器人坐标冻结，恢复后从原地/原等待状态继续。
5. 在动作或失败收尾过程中重启后端：页面进入「待人工核实恢复」，可先登记迟到回应，再选择继续收尾或结束；再次重启后已保存决定不重复询问。
